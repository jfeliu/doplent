System map · Sept 2026

Doplent Architecture

A Django app that helps one primary/pre-primary school cover teacher absences: a teacher reports when they're away, the app works out who is genuinely free during that window, and offers get sent, accepted, and turned into a booked substitution.

Runtime

The stack

Server-rendered Django, deployed as a single container on Fly.io. There is no SPA, no API layer, and no task queue — a request comes in, templates render, the response goes out. Everything reactive on the page is a small block of vanilla JavaScript inside the template it belongs to (the date picker, the substitute-picking grid).

The whole dependency list is five packages: Django, dj-database-url, psycopg, whitenoise, gunicorn. Front-end assets (Bootstrap 5, Bootstrap Icons, the Inter typeface) load from a CDN rather than being vendored or bundled.

Domain

Two apps, one job

teachers owns who's around and when. substitutions owns arranging cover and calls into teachers for availability. The interesting logic lives in plain modules — services.py, offers.py, emails.py — not in the views, which stay thin.

teachers

the roster and the timetable

  • Teacher — one-to-one with a Django auth user; grade level, active flag.
  • WeeklyNonTeachingHours — recurring free blocks per weekday, each tagged with a kind: free, paperwork, co-teaching, or escolta'm. A co-teaching block also names its head teacher — when the head is absent the co-teacher holds the room, so the picker asks for no substitute then (unless the co-teacher is already busy).
  • NonTeachingHoursPriority — admin-editable ordering that says how readily the picker pulls a teacher off each kind.
  • importer.py — all-or-nothing CSV bulk import of teachers and their hours, tolerant of Excel's cp1252; also exports the current roster back out in the same format.
  • calendar.py — lays the whole roster out as one week-grid for the admin, with a one-click CSV export of what it shows.
  • Self-service schedule editor at /schedule/.

substitutions

matching, offers, notifications

  • Absence · Substitution · SubstitutionOffer — reported, booked, and pending-decision records.
  • services.py — the matching engine: what needs cover, who's free, and build_coverage_grid() (30-min slots × eligible teachers, ranked by fairness).
  • offers.py — the offer lifecycle: create, accept (→ book), decline, and lazy expiry.
  • emails.py — four notifications; the confirmation carries a hand-rolled .ics so the slot lands on a calendar with no calendar API.
  • stats.py — course-to-date figures for the admin dashboard.
  • dates_ca.py — Catalan weekday and time-range formatting.

Data

Data model

Six tables. An Absence fans out to any number of Substitutions (one teacher rarely covers a whole day) and any number of SubstitutionOffers. An accepted offer points one-to-one at the Substitution it produced.

Core flow

How a substitution gets arranged

Nothing is booked without the candidate's consent. Picking a teacher sends a pending offer; a confirmed Substitution only exists once someone accepts.

  1. A teacher reports an absence — date, time range in 30-minute steps, reason. The form refuses a window with nothing to cover (all lunch, all outside hours, or entirely the reporter's own free time).

  2. They land on the picker. build_coverage_grid() draws 30-minute rows across the absence — non-cover stretches shown as labelled bands — and a column per teacher free for at least one slot that still needs cover.

    Columns lead with the narrowest availability, then whoever has covered least this school year. Cells are coloured by non-teaching kind.

  3. Whoever's arranging cover clicks free cells to build periods and hits Send offers. One SubstitutionOffer (pending) per contiguous run per teacher, each with an email to the candidate.

    The period is now locked — no one else can be offered it until the candidate replies.

  4. Accept → accept_offer() creates the Substitution, emails a confirmation with an .ics attachment, tells the reporter, and expires any overlapping sibling offers.

    Decline (with a reason) → the reporter is notified and the slot opens back up in the grid, flagged red so you know who already said no.

  5. A pending offer whose window has passed is flipped to expired lazily — expire_stale_offers() runs at the top of the dashboard and picker views. There is no cron for it.

Ops

Runtime & operations

Everything below is free-tier or near it, chosen so one person can run it without a platform team.

hosting — fly.io
One shared-cpu-1x / 512 MB machine in ams, auto_stop_machines so it sleeps when idle. Docker image; the deploy release command runs migrations.
database — supabase
Managed Postgres over the session pooler (port 5432 — the direct host is IPv6-only). Local dev falls back to a SQLite file automatically.
email — brevo
SMTP relay. Sent synchronously inside the request with a bounded timeout; a teacher with no address on file is skipped silently. Dev prints mail to the console.
ci/cd — github actions
fly-deploy.yml ships every push to main. db-backup.yml runs nightly: pg_dump → gzip → GPG AES-256 → a private Google Drive folder, one-year retention.
front-end delivery
Bootstrap 5, Bootstrap Icons and Inter from jsDelivr / Google Fonts. WhiteNoise serves the app's own hashed static files. No build step.
i18n
Catalan is the default for everyone via a custom middleware that ignores Accept-Language; English stays available through an in-app cookie switch.

Deliberately absent: no Celery or Redis (offers expire on read, mail sends in-request), no REST framework or SPA (server-rendered templates), no CDN for the app's own assets, and no calendar-provider integration (the .ics file is built by hand). The trade is latency spikes on cold email sends against having almost nothing to operate.
